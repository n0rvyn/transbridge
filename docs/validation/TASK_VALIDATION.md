# 数据判断规则

公开任务方法与检查流程。真实账号结果、个人佩戴习惯与逐次验证记录保存在忽略的本地日志，不随插件分发。

## 先选判断方法，再选数据范围

不能从“负荷”二字自动选 7 天、14 天或 28 天。先说明用户要判断的具体问题，定义指标、结束日期、时区和理论依据，再读数据。返回的记录数量不能反过来决定观察窗口。

| 问题 | 可用依据 | 窗口选择规则 | 不允许的推断 |
| --- | --- | --- | --- |
| 当前训练周做了什么 | UESCA 经典周期化：微周期通常为一周，中周期由 2–6 个微周期组成；PDF 第 471 页 | 用实际计划微周期；未提供计划时，明确说明使用自然周或截至指定日期的连续七天，并标注这是分析约定 | 一周是所有人的固定生理恢复周期 |
| 是否增加训练量／训练压力 | Daniels 第 44–45 页将压力区分为量、强度、恢复和频率；第 84–85、87 页建议同一周量维持约 3–4 周再增加 | 对照计划阶段和此前 3–4 周稳定性；选择具体四周是基于教材原则的分析设计，不是教材规定的唯一 API 读取窗口。本轮历史演示采用四个完整训练周；新同步演示采用截至最新记录的四个连续七天区段 | 把距离变化直接等同生理负荷；把 28 天当作所有问题的固定答案；凭一个百分比认定过度训练 |
| 今天是否恢复充分 | UESCA 第 211 页：HRV 是多项恢复信息之一；第 486 页区分短期疲劳与功能性过度负荷 | 结合训练任务、近期表现、主观反馈与实际存在的恢复记录；未核实个人基线时，不自动使用统一天数或 HRV 阈值 | 没有睡眠／HRV就表示睡了零小时或恢复正常；单次异常足以诊断过度训练 |
| Garmin 的 Acute／Chronic Load 数值代表什么 | Garmin 官方产品指标说明；与教材训练原则分开 | 优先读取服务实际指标并核对其日期。官方说明 Chronic Load 为过去 28 天 Acute Load 的加权平均；不得用简单活动负荷加总冒充加权指标 | 把 Garmin 产品窗口或显示区间冒充 Daniels／UESCA 的普适生理阈值 |

教材出处：Jack Daniels, *Daniels’ Running Formula*, Human Kinetics (2021)，项目持有 PDF；UESCA *Running Coach Certification Full Course*, V2_3-16-26，项目持有 PDF。页码为 PDF 从 1 起算。这里只记录核对后的规则，不随插件分发教材。

Garmin 指标来源：[What Is Training Load on My Garmin Device?](https://support.garmin.com/en-CA/navionics/faq/SEkNpdGyhR917js0qQL3Q6)。产品文档只解释产品指标，不用作个体训练处方。当前已核对的教材内容未给出适用于所有恢复问题的统一七天／十四天取数公式。

## 每个数据任务的检查流程

1. 核对服务身份与区域。按用户问题和出处定义时间范围及指标；未来排课与历史活动使用不同资源 ID。
2. 活动／装备／模板列表读至实际结束。下一页偏移按返回行数前进；记录每页行数、空页和服务总数（存在时）。按稳定 ID 去重并报告重复，不把请求页大小当作结果上限。若上游重复同一页、ID 冲突、总数变化或日期漂移，先处理不一致，不发布完整结论。
3. 日期查询与完整列表按活动的当地日期过滤结果比较 ID 集合；检查上下界和月份索引。按活动实际返回的时区处理；个人设置返回的 gmt 字符串不能直接覆盖活动的真实时区。
4. 核对每个响应内的日期、资源 ID 与所有者，不能将训练状态中的“最近记录”默认当成请求当天。没有记录不等于没有发生运动；同步覆盖不足时，不能假设已有完整基线。
5. 图表先检查 metricDescriptors、metricsCount、totalMetricsCount、数组长度、可用状态、时间范围和缺失点。按实际 totalMetricsCount 重新指定 maxchart，逐次核对点数；maxpoly=0 只用于本任务无需轨迹的读取，不能用于需要路线几何的任务。若仍缺点，报告限制，不计算依赖完整序列的结果。
6. 用 metricsIndex 定位各列，实际样本核对单位。不能假定列顺序固定，也不能仅凭 unit.factor 对所有数值再次缩放；实测图表 sumDuration、sumDistance 已以秒、米给出。
7. 距离由米转换，时长按秒处理，速度按 m/s 处理。展示 Garmin 配速时使用服务 averageSpeed；duration/distance 是独立复算，会受服务速度精度与计时口径影响，不能强制要求逐秒相同。对照网页同一单位、字段和取整方式。
8. 核对分段总距离／总时长与汇总，并解释存储精度。先区分热身、工作段、恢复与收尾；间歇课不能当作同配速匀速跑直接给出“有氧漂移”。如果要报告漂移，先给出方法出处、可比区段和环境影响；没有依据时只报告实际观察。
9. 睡眠响应有外层对象不代表有睡眠记录；例如 dailySleepDTO.sleepTimeSeconds=null、levels=[] 或 HRV={}，都不能据此推断恢复正常。保留 null、缺失、数值零和错误的区别，不制造恢复判断。
10. 结论附上实际覆盖日期、缺口及结论的适用范围。非空样本证明本次字段与处理兼容，不证明其它运动类型、全部分页场景或所有格式已覆盖。

继承限制：固定依赖 garminconnect 0.3.17 的 get_activities_by_date 使用每页 20 条和 MAX_PAGINATED_REQUESTS=2000 的请求保护；达到保护时抛错，不能声称完整成功。完整性检查应使用显式 get_activities 分页到空页，不把该保护或默认图表 2000 点变成产品数据上限。工具当前保持原始响应格式，不额外裁剪。

## 可重复验证

真实任务执行前必须核对账号、源模板、未来测试日期与用户授权。现有入口 scripts/verify_garmin_live.py 执行临时计划往返并清理；绝不随离线测试自动写入账号。活动与图表完整性按上方命名工具检查流程执行，不能用独立脚本或 mock 代替聊天可用性。

回归关注：分页超过一页、空结果、真实工作／恢复分段、单位换算、日期边界、图表采样、不完整基线、null 不等于零、列表重复 ID、测试资源清理和宿主缺工具。私有响应仅留临时文件用于本轮核对，不纳入源码、发布包或可视化。
