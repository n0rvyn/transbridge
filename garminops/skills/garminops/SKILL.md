Use the six Garmin MCP entry points. Search with garmin_search_tools, fetch the exact definition with garmin_describe_tool, then pass operation, schema_hash and arguments to garmin_read_tool or garmin_write_tool. All 151 registered operations remain available; named operations below are catalog IDs, not eagerly exposed tools. Never invent operation IDs or bypass the registered catalog. Start with `garmin_connection_status` and `garmin_account_identity`. Identify the actual Garmin service account; never use a browser profile name as its identity. Respect the user's explicitly authorized account and region. If the authorized account is not established, obtain identification/authorization before business reads or writes; saved credentials do not grant access. In a development checkout, follow the repository's public AGENTS.md and any existing local AGENTS.override.md restrictions; these local rules are not distributed with the plugin. Pass the returned Garmin account ID as `expected_account` for writes; stop before resource operations if the identity differs from the requested account.

Past facts are immutable: never create/import/edit/delete/recalculate activities or other logged health data, including activity names, descriptions, sets, and gear assignments. The connector exposes no historical write tools. Do not use another client to bypass this restriction.

Workout templates and calendar plans are distinct. Use create/copy/update/delete for templates; schedule/unschedule/reschedule for scheduled instances. Calendar scheduling does not deliver anything to a watch. Device actions need separate authorization and are not registered in this build.

Writes must correspond to the user's requested change. A permitted category is not an instruction to make arbitrary changes. Preserve unrelated settings. Settings mixed with observations require a verified field contract.

A write is confirmed only when `verified` is true. On an error after a request was sent, inspect `completed_requests` and `last_request`; read the affected resources before retrying. Rescheduling creates the replacement first, then removes the original. A failed second step can leave both schedules. Do not repeat creation blindly.

Heart-rate setting tools accept numeric configuration updates for an existing sport. Garmin ignored null during real tests: clearing an existing threshold to null remains unresolved. Report this limitation; do not describe zero as equivalent to unset. The user accepted FTHR null restoration as known issue KI-001 and explicitly stopped further tests or restoration attempts. Do not probe, try sentinels, or retest this issue unless the user explicitly reopens it. Resolving KI-001 is not a requirement for this release.

Read results retain upstream data shapes. Paginate until exhausted and inspect duplicate IDs; never infer complete coverage from a default page. The test account returned 12 workout rows representing 11 unique templates. Compare resources by stable ID and report duplicates explicitly. Empty device data does not prove a general platform limitation.

The selected product scope is Codex/ChatGPT desktop local plugins using local Garmin login. Remote hosting is outside this scope. One default server follows the region selected by a successful local login; no cross-region sync.

This development build has 116 SDK read adapters plus fixed course-list, course-detail, effective-daily-goal, independent-calendar-note, calendar-event and four gear readers, account identity/status, and 24 named writes. International workout/calendar and max-HR MCP roundtrips, plus installed-package copy/delete, have been verified. Other fields, capabilities, China-region live behavior, retain their stated verification gaps in ../../../docs/operations/RUNNING.md and ../../../docs/validation/LIVE_VERIFICATION.md. Do not present the entire capability inventory as completed support.


Use `garmin_update_power_zones` for an existing sport's FTP or explicit watt boundaries. Garmin linked cycling FTP changes to cross-country-ski FTP and zone values in live verification. Tell the user this observed effect when proposing a cycling FTP change, and report `linked_profile_changes` from the result. Do not claim only cycling changed. The requested profile is verified exactly; other unexpected sport/field changes remain errors. Zero is the numeric value zero, never a substitute for null. This does not send settings to a device or change logged records.


Use `garmin_update_measurement_system` for an explicitly requested display-unit change. Pass the exact Garmin key, such as metric or statute_us; never choose a default without the user specifying units. It sends only measurementSystem and verifies the full profile, preserving unrelated fields. Other profile fields, including weight and logged values, are not accepted by this tool or its outbound route. Read current units using garmin_get_unit_system.

Use `garmin_get_userprofile_settings` to read current locale, time zone, date/time format objects and display units. This is distinct from the user profile and returns upstream nulls and nested format metadata unchanged.

Use `garmin_get_effective_goals` with an explicit YYYY-MM-DD date for daily goal settings effective that day. `garmin_get_goals` reads independent active/future/past training goals; an empty list there does not mean daily goals are absent. Neither reader changes goals or recorded progress.

Use `garmin_create_goal`, `garmin_update_goal`, and `garmin_delete_goal` for independent future training goals. Start date and privacy must be explicit. Current contracts reject started/completed goals or goals with recorded progress; support for changing those remains unverified. Daily effective goals have no write tool. Goal definitions contain name, activityType, period, type, startDate, privacy, and four target fields; exactly one matching the type is non-null. Never pass progress, remaining, overage or completion fields. On partial failure recover the created id from completed_requests; do not repeat creation blindly.

Use `garmin_get_calendar_note` to read an independent calendar note. Use `garmin_create_calendar_note`, `garmin_update_calendar_note` and `garmin_delete_calendar_note` only for explicitly requested future planning notes. Note writes accept only id, noteName, content and date; activity annotations and training-plan task notes are separate resources and have no write permission through these tools. Verify read-back and calendar presence. Moving a note must remove it from the original date. On partial failure inspect the returned created ID before retrying.

Keep existing region-aware login; do not switch region or request a paid subscription to unblock this release. Use `garmin_get_calendar_event(event_id)` to read a calendar event and its activity/plan associations. These fields are preserved, not forwarded into writes. Use garmin_create_calendar_event, garmin_update_calendar_event and garmin_delete_calendar_event for explicitly requested independent future private events. Writes require a complete known definition and reject activity associations, results, primary/training-plan links, shared/official events and unknown state. Course/image attachment and other event contracts remain unverified. Never forward eventCustomization into a write. Every operation verifies details and calendar state; deletion requires a 404.

Use garmin_get_gear_items with explicit start/limit/status; paginate ACTIVE and RETIRED separately until empty for the full modern gear inventory; garmin_get_gear_item reads a canonical UUID and preserves usage/association metadata. garmin_get_gear_usage_types reads the usage-tracking catalog. Use garmin_create_gear, garmin_update_gear and garmin_delete_gear for explicitly requested unused independent gear with no default activities. Usage tracking supports NONE, DISTANCE (meters), DURATION (seconds) and DATE (ISO date); explicitly provide inactive numeric thresholds as zero and inactive date as null. Use garmin_set_gear_status to retire or reactivate unused independent gear; editing/deletion requires ACTIVE status. The tools reject any recorded usage, missing association counts, processing, images, collections or unknown state. Default conflict replacement, preferred defaults and used gear contracts remain in development; never use activity association endpoints to change history. On partial creation failure, inspect the returned uuid in completed_requests before retrying.

Use garmin_get_gear_default_choices with an explicit gear_type such as SHOES or BIKE to read activityTypeKey/defaultGearUUIDs mappings. An empty response means no defaults for that queried type. Use garmin_set_gear_defaults for explicitly requested future defaults on unused active independent gear. Pass the complete desired activities list with activityTypeKey, defaultGear true and preferredGear false; [] clears all defaults for that item. Existing conflicts and preferredGear true remain unverified and are rejected before writing. Clear defaults before editing, retiring or deleting gear through the current tools. Never substitute historical activity assignment endpoints.

Use garmin_get_gear_activities with explicit gearUUID, start and limit. Continue by returned row count until an empty page; the connector does not clamp the requested limit. Do not infer populated-history coverage from empty test-gear results. garmin_get_gear_stats preserves upstream totals and UUID formatting; a missing resource remains an error, not a zero-use result.


## Task-based data checks

Read ../../../docs/validation/TASK_VALIDATION.md before training-load, recovery or detailed-run analysis. Define the question, metric, dated window, time zone and source before fetching. Training theory comes from a checked source, not the number of available rows. UESCA uses a week as a typical microcycle; Daniels recommends holding weekly amount for about 3–4 weeks before increasing it. These principles inform a task-specific analysis window; they are not a universal 7/14/28-day rule. Treat Garmin's proprietary load definitions separately and do not reconstruct weighted load from a simple sum of activity loads.

For complete activity history use explicit get_activities pages until exhausted; compare stable IDs and count_activities, and cross-check date-query IDs with local-date filtering. Report duplicates, changed totals, missing baseline and endpoint errors. A short nonempty page is not termination proof. A period with no synced records is not proof of no training.

Before time-series analysis compare metricsCount, totalMetricsCount and activityDetailMetrics length. If sampled, request maxchart equal to the actual reported total and verify the returned rows, timestamps and missing values. Use maxpoly=0 only when geometry is unnecessary. Resolve metric positions through metricDescriptors; verify actual units against summary and lap values before scaling. Do not apply unit.factor blindly. If complete data remains unavailable, report the gap and withhold only conclusions that require it; do not silently truncate.

For real nonempty runs compare list, summary, laps and chart data, units, resource IDs and local dates. Identify warmup, ACTIVE, RECOVERY and cooldown before interpreting intensity or drift. Do not report uniform-pace decoupling for a mixed interval workout. Preserve null, missing, zero and errors as different states. Empty sleep/HRV is valid when the user does not wear Garmin daily; do not infer recovery, substitute Apple Watch data, or require different wearing habits just to finish a test.

Before a natural-language workflow, verify that the needed named tools exist in the actual host conversation. Independent installed MCP success does not establish host exposure. If a needed tool is absent, report the exact missing tool and evidence; do not silently replace the workflow or mark host acceptance passed.
